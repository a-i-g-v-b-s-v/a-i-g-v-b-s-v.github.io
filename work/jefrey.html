J.E.F.F.R.E.Y

A local-first voice assistant that listens, plans and acts on a Mac, and wrote the daily fund note for A.R.I.S while that system ran.

  • 3model backends behind one router: Claude, OpenAI and a local model through Ollama
  • 680 msSIMmedian time to the first spoken word on the local path
  • 71%SIMof turns answered without leaving the machine
  • 6sections in the daily fund note it wrote for A.R.I.S

J.E.F.F.R.E.Y is a voice assistant that runs on my own machine. It hears a request, decides what is being asked, sends it to a local model when that is enough and to a cloud model when it is not, carries out the steps on the Mac and answers out loud. A particle sphere in the browser shows what it is doing. Its second job was to write: on each day A.R.I.S ran, it turned the run into a one-page fund note.

01Why build one

The commercial assistants are good at conversation and poor at doing things on the computer in front of you. They also send everything to a server. J.E.F.F.R.E.Y starts from the other end: it lives on the machine, it can act on it, and it only reaches for a cloud model when the request needs one.

02The tools it is built from

Nothing here is exotic. The point of the design is that each job has one small, replaceable tool behind a common interface, so a better speech model or a cheaper language model can be dropped in without touching the rest.

03Scoring a request

Routing rests on one small function. It reads the request and adds points: for length, for words that signal code, research or planning, and for code blocks. Anything scoring below 7 out of 10 goes to the local model first; 7 and above goes to Claude or OpenAI.

The rule is crude on purpose. It runs in microseconds, it can be read in a minute, and when it sends something to the wrong place the reason is visible.

04A memory it can search

The assistant keeps what it is told in a local SQLite database with a full-text index, so recall is a search and not a guess. Conversations are stored by session. Separately it keeps learnings: patterns it has inferred, each with a confidence score, ignored until the score passes a threshold.

The whole system is 1,946 lines: a Python server for intent, routing, planning, memory and voice, and a TypeScript client for the microphone, the socket and the sphere.

05Routing: the smallest model that will do

Most requests are simple: open this, what is on today, how did the book do. A small local model answers them quickly and privately. A router reads the intent and its difficulty and escalates only the requests that need more: long reasoning, code, anything that reads the web.

An evaluator scores answers after the fact, so the routing rules are checked against outcomes and not left as guesses.

07Acting, not only answering

A planner turns a request into ordered steps and an action runner carries them out through three integrations: macOS itself for apps, files and settings, a browser for the web, and Claude Code for work in a repository. Each step is traced, so any action can be read back later with the request that caused it.

08Chief strategist for A.R.I.S

J.E.F.F.R.E.Y's second role was written. While A.R.I.S ran, from April to October 2026, after each run it received the regime, the positions and the top signals and wrote a one-page note in a fixed institutional format. The last section was the one that mattered: two or three conditions that, if they happened, would mean the current view was wrong.

10Always listening, and connected to my accounts

The n8n build starts on a wake word. A small offline detector listens continuously, so nothing is recorded or sent anywhere until the trigger is heard. The words after it are transcribed on the machine and posted to an n8n workflow.

Inside the workflow, Claude reads the request and hands it to one of four sub-agents, with an optional memory store beside them. The difference from the rest of this page is where they act: on the real Gmail and Google Calendar accounts through their own connections, not on the Mac's apps. The reply comes back as text and is spoken by ElevenLabs, while the display shows whether the assistant is idle, thinking or speaking and keeps the conversation on screen.

11Working before I ask

An assistant that only answers is a search box with a voice. This build runs on a schedule and on triggers. Each morning it compiles a briefing and reads it aloud, starting with how I slept, because that decides how the day should be planned. Through the day, background monitors watch markets, the calendar, the news and my own recovery, and interrupt only when something crosses a threshold.

The media feed behind it reads more than twenty sources in three tiers: the main financial papers, market sites, and a set of macro newsletters. Articles are scored against a list of macro and trading terms, so I can ask what one publication is saying about a subject and get the ranked answer.

12Records and keys

The assistant writes things down so that I do not have to. If I say I bought something, it logs the trade with the reason I gave. If I mention someone I met, that is logged too.

Keys are handled the same way I would want a colleague to handle them. Every login and API key lives in the macOS Keychain. A setup script reads them from there and configures n8n, so no key is written in the code or in a file in the repository. A shared memory bridge lets my other projects read and write the same store, so the assistant knows what the trading system last did.

13What a month of use looks like

The assistant does not yet keep long-run usage statistics, so these two charts are estimates of the pattern, not measurements. Most turns are conversation or quick system commands, which is why a local model can carry most of the load. Memory fills quickly in the first weeks, as standing facts and preferences are stated once, and slows after.
